# NOVA Vault Signed Identity Assertion — Architecture Candidate

**Status:** Candidate design for isolated proof only; not approved for staging or production  
**Control plane:** Existing Cloudflare System Integration Hub  
**Database path:** Dedicated nova_vault_api login through a cache-disabled Hyperdrive binding  
**Safety:** Read-only provider scopes only; Exness MT5 Demo remains read-only

## 1. The identity gap to close

The Local Vault Proof now demonstrates that the private accessor rejects mismatched owner, tenant, connection, provider, environment, generation, and lifecycle values. It does not yet prove that the caller is entitled to assert the owner and tenant identifiers it supplies.

An attacker who has obtained the dedicated database login could submit Customer B's real owner, tenant, and connection identifiers. A check that compares a caller-supplied owner ID with a connection row is not authentication when the caller can choose both values.

Before staging, the database must verify a short-lived cryptographic assertion created only after the existing System Hub has authenticated the customer and resolved the connection from trusted server-side data. Do not treat a plain UUID, an HTTP header, a client-provided JWT claim, or a free-form SQL parameter as proof of identity.

## 2. Candidate protocol

Evaluate an HMAC-SHA-256 assertion generated by the existing System Hub and verified inside the private SQL accessor.

- The System Hub signs with a per-environment 256-bit random key held as a Cloudflare Worker Secret.
- The matching verifier key is provisioned as a versioned Supabase Vault secret. The non-login nova_vault_fn_owner function boundary reads it from the Vault decrypted view. The runtime login nova_vault_api must never receive direct Vault access or the verifier key.
- The key ID is server-selected. A caller cannot select an arbitrary Vault reference or enable a retired key.
- The key is not stored in Git, migrations, ordinary application tables, browser configuration, model context, MCP payloads, logs, traces, or CI output.
- Local tests use synthetic keys only. Staging and production receive independently generated keys through a controlled out-of-band process.

This is a symmetric design: the Worker signer and database verifier hold the same key material. A compromise of the Worker signing environment can mint assertions for arbitrary owners. A compromise of the privileged Supabase service_role / project-admin boundary can access Supabase-managed Vault grants; this protocol does not protect Secrets from that privileged boundary. Supabase documents that Vault installation grants service_role access to Vault tables, views and selected functions, and that postgres cannot revoke platform-managed grants made by supabase_admin. If the product threat model requires a compromised service_role identity to be intrinsically unable to read any customer Secret, stop and use a separately managed secret-custody service instead of claiming Supabase Vault provides that boundary.

## 3. Who creates the assertion

The System Hub creates an assertion only after all of these checks:

1. Verify the Supabase bearer token through the existing Hub authentication path and obtain the authenticated user ID from the Auth response.
2. Resolve the exact connection using the customer's own session / RLS path. Never accept an arbitrary owner ID or connection-to-owner mapping from the browser, AI, MCP, or generated UI.
3. Resolve the tenant from the canonical server-side tenant registry if one exists. The current Worker connection query selects user_id; do not invent or accept a tenant ID until the actual tenant mapping is verified. For a single-owner connection model, bind owner_id and connection_id and record that tenant_id is not yet part of the verified schema contract.
4. Check provider and environment against a server-owned allowlist, connection status, required read-only capability, current secret generation, and lifecycle state.
5. Create the operation ID and fresh nonce on the server. The client cannot choose either value to replay an old assertion.
6. Select the active key ID from trusted Worker configuration and sign the canonical message.

The database remains the second authorization boundary. A valid signature never bypasses a current database ownership, tenant, connection, provider, environment, capability, status, or generation check.

## 4. Signed claims and canonical message

Protocol version 1 contains these fields:

| Claim | Rule |
|---|---|
| version | Fixed integer 1 |
| issuer | Fixed value voom-system-hub |
| audience | Fixed value nova-vault-access |
| key_id | Server-selected active key identifier |
| owner_id | Authenticated Supabase user UUID |
| tenant_id | Server-resolved canonical tenant UUID only when the verified schema has one |
| connection_id | Exact server-owned connection UUID |
| provider | Server-owned registry value |
| environment | Exact allowlisted environment |
| capability | One fixed read-only capability |
| generation | Current expected secret generation |
| operation_id | Stable idempotency identifier for the logical operation |
| nonce | Fresh cryptographically random UUID per assertion |
| issued_at | UTC Unix epoch seconds |
| expires_at | UTC Unix epoch seconds, no more than 60 seconds after issued_at |

Do not sign arbitrary JSON and depend on property ordering, whitespace, or number formatting. Both sides must build the same UTF-8 canonical message with a fixed field order and one line per value:

    NOVA-VAULT-ASSERTION-V1
    issuer
    audience
    key_id
    owner_id
    tenant_id-or-empty
    connection_id
    provider
    environment
    capability
    generation
    operation_id
    nonce
    issued_at
    expires_at

Reject CR, LF, delimiters, NUL, unbounded strings, non-canonical UUIDs, unsupported enum values, leading-zero numeric encodings, and missing required claims before building the message. The tenant slot is an empty value only in the explicitly approved owner-only model; do not let the caller decide whether tenant binding is optional.

The Worker uses Web Crypto through crypto.subtle.importKey and crypto.subtle.sign with HMAC and SHA-256. The signature is exactly 32 bytes. PostgreSQL pgcrypto provides hmac(data bytea, key bytea, type text) returning bytea; the isolated proof must first establish that pgcrypto is available in the exact local and target database and resolve its actual schema. Do not use MD5, SHA-1, or a custom JavaScript cryptography implementation.

## 5. Database verification contract

The private accessor must verify the assertion before resolving any customer Secret:

1. Resolve key_id through a private server-owned key registry. The caller cannot supply a Vault secret ID, verifier key, or SQL identifier.
2. Load the corresponding verifier key only inside the reviewed non-login function-owner boundary.
3. Reconstruct the canonical message from typed arguments using the same field order, UTF-8 encoding, UUID normalization, enum allowlists, and decimal integer representation as the Worker.
4. Calculate the expected HMAC-SHA-256 and compare the supplied 32-byte MAC. The comparison helper must reject wrong lengths and perform a fixed 32-byte accumulation without an early exit on the first differing byte. This is fixed-work application logic, not a claim of formally constant-time execution by the PostgreSQL runtime; it requires independent security review and timing scrutiny. Keep the database route private, bounded, rate-limited and inaccessible through the Data API.
5. Verify fixed version, issuer and audience; issued_at must not be materially in the future; expires_at must not be expired; expires_at - issued_at must be positive and at most 60 seconds.
6. Re-check the current owner, tenant (when supported), connection, provider, environment, capability, status and generation against the authoritative registry.
7. Insert the nonce into a private replay table with a unique constraint on key_id and nonce. The insert is atomic. A duplicate nonce fails closed. Bound replay retention and cleanup; do not hold a long-lived lock or transaction during provider calls.
8. Return only the material required to the trusted System Hub process. Never return the assertion key, signed message, signature, or customer Secret to the browser, AI, MCP, logs, traces, audit events or analytics.

The Hub must treat an ambiguous database or provider timeout as an unknown operation outcome and reconcile by operation_id. A retry may receive a fresh nonce while retaining the same logical operation_id; the Hub idempotency store must prevent duplicate provider operations. A replayed assertion with the same nonce is rejected.

## 6. Key lifecycle

- Use a separate random 256-bit key for local proof, staging and production.
- Identify the key by key_id; do not infer a key version from key material.
- Allow one active signing key and, only during an approved rotation window, a previous verification-only key.
- Provision the new verifier key in the private Vault registry before deploying the Worker signer that uses the new key ID.
- Switch the Worker signer, allow at least the maximum assertion lifetime plus clock-skew allowance, then disable and retire the previous key.
- Never put actual key bytes in migrations, fixtures, CI variables, repository files, build output, or chat.
- Audit key lifecycle events with key IDs, timestamps, actor identity and outcome only.
- If signer/verifier state diverges or key rotation is ambiguous, fail closed and require controlled recovery.

## 7. Required local proof additions

Extend only the disposable tools/vault-proof project. Do not alter the canonical Supabase migrations or hosted database.

The expanded proof must demonstrate:

1. A valid Customer A assertion can access only A's synthetic fixture.
2. A valid Customer B assertion can access only B's synthetic fixture.
3. Customer A cannot forge Customer B claims without the signing key, even when A knows B's owner, tenant and connection UUIDs.
4. Changing owner, tenant, connection, provider, environment, capability, generation, issuer, audience, key ID, operation ID, nonce, issued_at or expires_at invalidates the signature or a policy check.
5. Expired and materially future-dated assertions are rejected.
6. A duplicate nonce is rejected atomically.
7. A fresh nonce with the same operation ID follows the idempotency rule and cannot repeat a provider operation.
8. A revoked connection, stale generation, wrong provider/environment, or unsupported write capability is denied even when a signature is otherwise valid.
9. The runtime role cannot read the verifier key, Vault tables/views, key registry, replay table, or cryptographic extension functions directly.
10. The function owner cannot call unrelated Vault functions or access unrelated application/customer tables.
11. No key, signature, canonical message, or plaintext Secret appears in SQL errors, CI output, HTTP responses, logs, chat, MCP or audit output.
12. Cross-runtime known-answer tests produce identical 32-byte HMAC results for Worker Web Crypto and PostgreSQL pgcrypto.

Passing local tests is not evidence of Cloudflare Worker secret provisioning, Hyperdrive cache disablement, Supabase Free IPv6 reachability, hosted role privileges, tenant mapping correctness, or independent staging customer A/B acceptance.

## 8. Alternatives and explicit limits

- Do not use pgjwt for this protocol: Supabase documents it as deprecated on PostgreSQL 17.
- Do not treat direct-connection session variables or caller-controlled JWT claim settings as signed identity. A database client controlling the connection can set them.
- Do not give nova_vault_api membership in service_role, postgres, pg_read_all_data, or pg_write_all_data.
- Do not expose the Vault schema or any function that returns decrypted Vault data through the Data API.
- Asymmetric signatures would avoid distributing a signing secret to the database, but no PostgreSQL Ed25519 verification implementation has been approved or proven in this repository. Do not claim that Cloudflare's Ed25519 support alone means PostgreSQL can verify Ed25519. Evaluate an asymmetric verifier only with a vetted, supported database implementation and independent tests.
- If HMAC key duplication or the privileged Supabase service_role trust boundary is unacceptable, stop and evaluate a separately managed secret-custody or assertion-verification service before any staging work.

## 9. Activation boundary

This document is a design candidate only. It does not create an HMAC key, add a database table or function, configure Hyperdrive, change the System Hub Worker, accept customer credentials, apply a hosted migration, or enable a customer credential route. The existing Local Vault Proof is a separate milestone and does not remove this signed-identity blocker.
