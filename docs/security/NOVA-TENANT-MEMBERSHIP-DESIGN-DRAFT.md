# NOVA Tenant Membership & Isolation — Design Draft

**Status:** DESIGN ONLY — NOT APPROVED FOR DATABASE APPLICATION  
**Baseline:** `main` at `821db357d70d3613b0ca61520eaae5c5307e8fd4`  
**Supabase project inspected read-only:** `rovhmjeowracayicbqij`  
**Branch:** `design/nova-tenant-isolation-20261125`

## 1. Decision summary

NOVA currently demonstrates **per-user ownership** for selected resources, not a general multi-tenant workspace model. The live catalog inspected on 2026-11-25 contains no tenant or tenant-membership relation in the `nova` or `public` application schemas.

Do not reinterpret an existing `user_id`, `requested_by`, or `actor` column as `tenant_id`. A tenant is a separate security boundary with explicit membership and tenant-scoped roles.

This document defines the target model and its test contract only. It adds no SQL migration and authorizes no DDL, RLS, grants, data changes, or Supabase settings changes.

## 2. Read-only evidence from the selected project

Observed application relations:
- `nova.approvals`
- `nova.audit_events`
- `nova.emergency_stops`
- `nova.mt5_broker_connections`
- `public.affiliate_state_snapshots`
- `public.nova_broker_connections` (view over `nova.mt5_broker_connections`, with `security_invoker=true`)

No `tenants`, `tenant_memberships`, or `workspace_memberships` relation was returned by the catalog query.

Observed ownership fields:
- `nova.mt5_broker_connections.user_id` is NOT NULL; existing policies permit SELECT of own rows and INSERT of own pending Exness MT5 Demo requests only.
- `nova.approvals.requested_by` / `decided_by`, `nova.audit_events.actor`, and `nova.emergency_stops.requested_by` are nullable UUIDs with existing SELECT policies based on `auth.uid()` and role checks.
- `nova.current_role()` reads `auth.jwt() -> 'app_metadata' ->> 'nova_role'`. This is a global NOVA platform role claim; it is not tenant membership and must not be treated as proof that a user belongs to a tenant.
- `public.affiliate_state_snapshots` has RLS enabled with no policies. Current grants returned no `authenticated` or `anon` access for this table; preserve it as server-only Affiliate state pending a separate project-boundary review. Do not add a client policy merely to silence the Advisor.

The selected project has a separate migration-reconciliation blocker documented in `docs/governance/NOVA-SUPABASE-MIGRATION-RECONCILIATION.md`. Tenant-model work must not bypass its backup/PITR, migration-provenance, or schema-drift gates.

## 3. Target data model

### `public.nova_tenants`

| Column | Type | Rule |
|---|---|---|
| id | uuid | Primary key, generated by database |
| slug | text | Unique, normalized, bounded length |
| display_name | text | Required, bounded length |
| status | text | `active`, `suspended`, `closed` |
| created_by | uuid | FK to `auth.users(id)`; set only from `auth.uid()` |
| created_at / updated_at | timestamptz | Database timestamps |

### `public.nova_tenant_memberships`

| Column | Type | Rule |
|---|---|---|
| tenant_id | uuid | FK to `nova_tenants(id)`, cascade only after reviewed lifecycle policy |
| user_id | uuid | FK to `auth.users(id)` |
| role | text | `owner`, `admin`, `operator`, `viewer` |
| status | text | `invited`, `active`, `suspended`, `revoked` |
| invited_by | uuid | Authenticated inviter; nullable for initial owner row |
| created_at / updated_at | timestamptz | Database timestamps |
| accepted_at | timestamptz | Nullable until accepted |

Constraints:
- Primary key or unique constraint on `(tenant_id, user_id)`.
- A tenant must have exactly one active owner at all times; owner transfer is an atomic privileged operation.
- At most one pending invite per `(tenant_id, normalized_email)` if email-based invites are introduced. Do not store raw invite tokens in this table.
- Role and status values are constrained at the database layer.
- A membership row cannot be self-created or self-promoted by an ordinary authenticated client.

### Tenant-owned application rows

New tenant-owned tables must include a non-null `tenant_id` FK and must enforce membership through RLS. If a resource is intentionally personal (for example, a broker connection), keep its current `user_id` ownership model until a separate product/security decision explicitly permits tenant sharing.

Do not add `tenant_id` to existing production tables as part of this design-only change. A later migration must include a reviewed backfill, orphan policy, indexes, constraints, and rollback/recovery evidence.

## 4. Authorization boundaries

Keep two separate role dimensions:

1. **Platform role** — existing signed `app_metadata.nova_role` claim, used only for explicitly global NOVA operator capabilities.
2. **Tenant role** — row in `nova_tenant_memberships`, scoped to one `tenant_id`, used for tenant data and tenant administration.

A global platform operator is not automatically a member of every customer tenant. Any break-glass access must be explicit, audited, time-bounded, and separate from normal RLS access.

Never authorize from `user_metadata`, client-supplied role strings, client-supplied `user_id`, or client-supplied `tenant_id` without checking membership in the database.

## 5. RLS and write-path design

The eventual migration must follow these rules:

- Enable RLS on both tenant and membership tables; consider FORCE ROW LEVEL SECURITY after checking trusted service workflows and table ownership.
- Tenant SELECT requires an active membership for `auth.uid()`.
- Membership SELECT permits a user to see their own membership; tenant admins may see members of their tenant.
- Authenticated clients receive only the minimum table grants. Do not grant direct membership INSERT/UPDATE/DELETE.
- Tenant creation is an atomic database function: require `auth.uid()`, create tenant, and create the caller's initial `owner` membership in the same transaction. Ignore any caller-supplied owner ID.
- Invitations and role changes use narrowly scoped functions that verify the caller has an active `owner` or `admin` membership in the same tenant. Prevent self-promotion, last-owner removal, and cross-tenant role changes.
- Any SECURITY DEFINER helper/function must use an empty or tightly fixed `search_path`, fully qualified object names, minimal ownership, explicit EXECUTE grants, and a documented reason that RLS recursion cannot be solved safely with invoker semantics.
- Every tenant-owned SELECT/INSERT/UPDATE/DELETE policy must compare the row's `tenant_id` to a membership check using the verified `auth.uid()`. INSERT and UPDATE require matching `WITH CHECK` predicates.
- The runtime must forward the end-user Supabase access token to a user-scoped Supabase client for tenant queries. Never use a service-role key in a user request path; service-role bypass is not tenant isolation.

## 6. Runtime integration contract

The VOOM AI Runtime's Supabase Auth middleware now verifies an access token and sets immutable `req.user.id`. This is an identity foundation only.

Before exposing tenant APIs:
1. Require a tenant identifier in the route/resource contract.
2. Resolve and validate active membership in the database for every request.
3. Pass the user's access token to Supabase so Postgres evaluates `auth.uid()` under that user.
4. Do not rely on `req.user.id` filtering alone as a substitute for RLS.
5. Do not trust a tenant ID cached in an unverified client session or supplied in a request body.
6. Return a generic not-found/forbidden response without revealing whether another tenant's resource exists.

The existing MT5 route registry is keyed by authenticated user ID plus connection ID and has an explicit read-only capability allow-list. Keep that per-user route boundary; do not widen it to tenant-shared broker accounts in this phase.

## 7. Required cross-tenant test matrix

Use two synthetic users (`user_a`, `user_b`) and two synthetic tenants (`tenant_a`, `tenant_b`). No production user or tenant records are needed.

| Test | Expected result |
|---|---|
| User A creates tenant A | One tenant and one owner membership created atomically |
| User A reads tenant A | Allowed |
| User B reads tenant A without membership | Denied |
| User B reads tenant A after active viewer membership | Allowed only for viewer-authorized operations |
| User B inserts a row with tenant A ID but no membership | Denied by RLS |
| User A attempts to insert a row with tenant B ID | Denied by RLS |
| User A changes own role to owner/admin | Denied |
| User A changes another tenant's membership | Denied |
| Tenant admin removes the last active owner | Denied |
| Suspended/revoked member accesses tenant data | Denied |
| Missing/invalid access token | Denied before tenant lookup |
| Client sends another user's `user_id` | Ignored; identity remains `auth.uid()` |
| Client sends forged platform role or `user_metadata` | No authorization elevation |
| Tenant A resource ID queried from tenant B | No data disclosure |
| Service-role path is used by ordinary user request | Architecture/test failure |

Tests must run against an isolated Supabase test target or local Supabase stack with two real test identities and seeded synthetic tenant rows. Mock-only policy tests are insufficient for final RLS proof.

## 8. Migration sequencing — future authorization required

1. Resolve the existing NOVA migration-ledger/source mismatch and verify a restorable backup or accepted logical export.
2. Confirm tenant product semantics: who can create tenants, invite members, transfer ownership, suspend tenants, and access audit records.
3. Write a forward-only migration in a separate PR; do not apply it to the selected project.
4. Validate schema replay from an empty isolated database and upgrade against a schema snapshot matching the selected project.
5. Run the full two-user RLS matrix, role escalation tests, and existing NOVA approval/MT5 read-only regression tests.
6. Review grants, function ownership, SECURITY DEFINER exposure, indexes, and migration rollback/restore plan.
7. Obtain separate explicit authorization before any production DDL or migration.
